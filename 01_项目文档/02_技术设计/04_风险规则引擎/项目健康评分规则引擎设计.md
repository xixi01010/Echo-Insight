# 项目健康评分规则引擎设计

> 当前治理说明（2026-09-05）：本文的确定性规则、评分与 AI 边界仍适用于 V3 Frozen；具体实现和验收结果以 V3 冻结验收记录为准。

## 1. 规则引擎职责边界

规则引擎位于飞书数据读取之后、AI Service 之前：

```text
Feishu Connector（只读）
        ↓
权限过滤与结构化整理
        ↓
项目健康评分规则引擎
        ↓
健康分数 + 健康状态 + L1-L5 风险等级 + 风险信号
        ↓
AI Service（只解释，不评分）
```

规则引擎负责：

- 根据已授权的结构化项目数据识别确定性风险事实。
- 计算 0-100 的项目健康分数。
- 为风险信号分配 L1-L5 风险等级。
- 合并重复或相关风险，避免重复扣分。
- 输出可追溯的证据引用和计算明细。
- 在输入不完整时产生明确的数据缺失信号。

规则引擎不负责：

- 调用模型或生成自然语言解释。
- 评价员工能力、态度或绩效。
- 跨项目推断未授权事实。
- 修改任务、负责人、Deadline、权限或其他飞书数据。
- 代替项目负责人决定是否采取行动。

规则引擎的结果是项目事实和可解释的计算结果；AI 只能基于这些结果生成 V2 协议规定的风险解释、影响分析、建议行动和限制说明。

## 2. 输入数据结构

规则引擎接收已完成权限过滤和字段标准化的数据，不直接读取飞书 API：

```json
{
  "project": {
    "id": "project-id",
    "name": "Echo Insight MVP",
    "sensitivityMode": "robust"
  },
  "tasks": [
    {
      "id": "task-id",
      "name": "完成数据读取",
      "owner": "成员甲",
      "status": "进行中",
      "deadline": "2026-08-30",
      "riskLevel": "L3",
      "isOverdue": false,
      "dependencyIds": [],
      "description": "完成 Base、Table、Record 读取链路"
    }
  ],
  "metadata": {
    "source": "feishu-base",
    "accessMode": "read-only",
    "authorizedProjectIds": ["project-id"],
    "generatedAt": "2026-08-22T00:00:00.000Z"
  }
}
```

输入约束：

- `project.id`、任务 `id` 和 `dependencyIds` 用于证据追溯，不由规则引擎改写。
- `status`、`deadline`、`isOverdue` 等字段必须来自授权数据或前置标准化过程。
- `isOverdue` 优先由统一日期计算得到；若缺少日期，不得猜测是否逾期。
- 规则引擎只处理当前授权项目范围，不跨项目补齐数据。
- Secret、Token 和完整未过滤 Base 不得进入规则引擎。

## 3. 风险信号定义

每个风险信号包含：

```json
{
  "code": "TASK_OVERDUE",
  "level": "L3",
  "taskId": "task-id",
  "evidence": "任务仍为进行中，截止日期为 2026-08-15，当前已超过截止日期。",
  "deduction": 15
}
```

### TASK_OVERDUE

触发条件：任务状态不是已完成，且截止日期早于统一计算日期，或标准化字段 `isOverdue=true`。

- 默认等级：L3。
- 默认扣分：15 分/个任务。
- 证据：任务 ID、状态、截止日期和计算日期。

已完成任务不因历史截止日期自动触发该信号。

### TASK_BLOCKED

触发条件：任务状态为阻塞，或标准化状态明确表示无法继续执行。

- 默认等级：L4。
- 默认扣分：25 分/个任务。
- 证据：任务 ID、阻塞状态和可用的阻塞说明。

阻塞原因缺失时仍可识别阻塞事实，但不得猜测具体原因。

### DEPENDENCY_BLOCKED

触发条件：任务依赖的前置任务存在，且前置任务处于阻塞状态或已触发不可继续的阻塞信号。

- 默认等级：L4。
- 默认扣分：20 分/条受影响依赖链。
- 证据：后续任务 ID、前置任务 ID 和前置任务阻塞信号。

同一依赖链只计算一次基础扣分，避免对每个重复引用进行重复扣分。

### MISSING_PROJECT_DATA

触发条件：项目或任务缺少规则判断所需的关键字段，例如项目 ID、任务 ID、任务状态、截止日期、风险等级或依赖关系信息。

- 默认等级：L2。
- 默认扣分：5 分/个缺失字段组，单个任务最多计 10 分。
- 证据：对象 ID、缺失字段名和受影响的规则。

缺失字段只产生数据质量风险，不得被解释为员工或项目执行能力问题。

## 4. L1-L5 风险等级定义

| 等级 | 名称 | 规则含义 |
| --- | --- | --- |
| L1 | 正常 | 当前规则未发现需要特别关注的风险信号。 |
| L2 | 轻微关注 | 存在数据缺失、临近节点或轻微偏差，建议持续观察。 |
| L3 | 一般风险 | 已出现延期或其他需要明确跟进的问题，可能影响后续进度。 |
| L4 | 严重风险 | 存在阻塞或依赖链问题，可能明显影响项目目标。 |
| L5 | 关键风险 | 存在多个高影响信号，或关键交付同时受到阻塞、延期和依赖影响。 |

等级用于描述项目风险严重程度，不用于评价个人能力、态度或绩效。

## 5. 100 分健康评分计算原则

- 初始健康分：100 分。
- 规则引擎根据去重后的风险事件进行扣分。
- 最终分数限制在 0-100 范围内：`healthScore = max(0, min(100, 100 - totalDeduction))`。
- 无风险信号且关键数据完整时，健康分为 100，健康状态为 `healthy`。
- 健康分只由确定性规则计算，AI 不参与计算、调整或四舍五入。
- 每次计算保留规则版本、输入快照时间、信号列表和扣分明细，确保可复核。

健康状态是分数的展示映射，不是模型判断：

| 健康分数 | 健康状态 |
| --- | --- |
| 80-100 | `healthy` |
| 60-79 | `needs-attention` |
| 0-59 | `at-risk` |

若存在 L5 关键风险，即使分数高于 60，也必须将健康状态至少标记为 `at-risk`，以避免分数掩盖关键信号。

## 6. 风险扣分规则

MVP 采用固定、可审计的基础扣分表：

| 信号 | 基础扣分 | 计分单位 | 说明 |
| --- | ---: | --- | --- |
| `TASK_OVERDUE` | 15 | 每个去重任务 | 同一任务只计一次。 |
| `TASK_BLOCKED` | 25 | 每个去重任务 | 阻塞任务优先于一般延期信号。 |
| `DEPENDENCY_BLOCKED` | 20 | 每条去重依赖链 | 同一前置任务导致的重复引用只计一次。 |
| `MISSING_PROJECT_DATA` | 5 | 每个缺失字段组 | 单任务缺失数据扣分上限为 10。 |

扣分顺序：

1. 标准化输入并识别所有信号。
2. 以任务 ID、依赖链 ID 和缺失字段组去重。
3. 对同一任务的多个信号应用合并规则。
4. 汇总扣分并计算健康分。
5. 根据最高风险和关键组合确定项目风险等级。

扣分表是 MVP 规则基线。后续调整必须更新规则版本和回归测试记录，不在 AI 层动态调整。

## 7. 多风险合并规则

- 同一任务同时 `TASK_BLOCKED` 和 `TASK_OVERDUE` 时，两种事实均保留，但基础扣分按较高的阻塞扣分计一次；逾期信号作为补充证据，不再次扣 15 分。
- 同一前置任务阻塞导致多个后续任务受影响时，`DEPENDENCY_BLOCKED` 按去重后的依赖链计一次；受影响任务列表全部保留用于展示和解释。
- `MISSING_PROJECT_DATA` 不与其他风险信号合并为执行风险，只作为数据质量风险单独记录。
- 同一任务、同一信号、同一输入快照不得重复计分。
- 多个不同任务的同类风险分别计分，但必须在输出中保留各自任务证据。
- 多风险项目的总扣分仍受 0 分下限约束。

## 8. 风险优先级规则

项目风险等级取去重后风险信号的最高等级，并应用以下组合升级规则：

1. 出现任一 L5 信号，项目等级为 L5。
2. 同一关键任务同时出现阻塞、逾期或依赖阻塞中的至少两类信号时，项目等级可升级至 L5；升级必须记录触发信号。
3. 无 L5 但存在 L4 信号时，项目等级至少为 L4。
4. 无 L4/L5 但存在 L3 信号时，项目等级为 L3。
5. 仅存在 L2 信号时，项目等级为 L2。
6. 没有风险信号且关键数据完整时，项目等级为 L1。

同等级风险的排序：先按扣分影响，再按截止日期临近程度，最后按稳定的任务 ID 排序。排序只影响展示顺序，不改变已计算分数。

## 9. 输出给 AI Service 的数据结构

规则引擎向 AI Service 输出规则结果和证据上下文。AI 可以解释这些结果，但不能覆盖其中的规则字段：

```json
{
  "projectContext": {
    "projectId": "project-id",
    "projectName": "Echo Insight MVP",
    "healthScore": 60,
    "healthStatus": "needs-attention",
    "riskLevel": "L4",
    "sensitivityMode": "robust"
  },
  "tasks": [
    {
      "taskId": "task-id",
      "taskName": "完成数据读取",
      "status": "进行中",
      "deadline": "2026-08-30",
      "dependencyIds": []
    }
  ],
  "ruleSignals": [
    {
      "signalId": "signal-1",
      "code": "TASK_OVERDUE",
      "level": "L3",
      "taskId": "task-id",
      "evidence": "任务超过截止日期。",
      "deduction": 15
    }
  ],
  "scoring": {
    "baseScore": 100,
    "totalDeduction": 40,
    "healthScore": 60,
    "ruleVersion": "mvp-v1"
  },
  "metadata": {
    "accessMode": "read-only",
    "generatedAt": "2026-08-22T00:00:00.000Z"
  }
}
```

AI Service 使用该结构生成 AI 输出协议 V2：`risks` 和 `limitations`。AI 输出不得包含或改写 `healthScore`、`healthStatus`、`riskLevel` 或任务状态事实。

## 10. MVP 阶段规则边界

MVP 支持：

- 单项目范围内的任务、Deadline、状态和依赖关系分析。
- 上述四类确定性风险信号。
- 固定 100 分制、L1-L5 等级和可审计扣分规则。
- 规则版本和证据引用记录。
- 将规则结果传给 AI Service 进行解释。

MVP 不支持：

- 跨项目风险聚合或未授权数据推断。
- 自动修改任务、负责人、Deadline、权限或项目文档。
- 员工能力、态度、绩效或责任归因判断。
- 通过 AI 重新计算健康分或风险等级。
- 预测性进度模型、机器学习权重或动态自适应扣分。
- 自动通知、自动执行或自主决策。
- 未经回归测试的规则权重变更。

本文件仅为规则引擎设计归档，不创建代码、不调用模型、不调用飞书 API，也不修改飞书数据。
